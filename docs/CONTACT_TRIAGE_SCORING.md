# ContactOps 2축 트리아지 계약

이 문서는 합성 연락업무를 위한 운영 검토 계약이다. 개인의 위험 확률, 복지 적격성, 고독사 가능성을 예측하지 않는다. 입력은 검증된 합성 ContactOps 상태, 조사원이 수집한 관찰값, 공개 동단위 맥락뿐이며 단전·단수 등 개인 위기정보 피드는 사용하지 않는다.

## 분리된 두 축

- `급성도_점수`(0~100): 지금 재연락·방문 검토가 얼마나 시급한지 나타내는 동적 운영 점수
- `취약도_점수`(0~100): 공개 동단위 맥락과 관계망 관찰을 나타내는 정적 운영 점수

두 점수는 합치지 않는다. `종합_점수`는 스키마에서 금지되며 큐는 급성도 내림차순, 취약도 내림차순, 마지막 성공 연결 후 경과일 내림차순, 케이스 ID 오름차순으로 정렬한다.

## 급성도 배점 v0.1.0

| 신호 | 가산점 |
| --- | ---: |
| 연속 미응답 1회 / 2회 / 3회 이상 | 0 / 25 / 45 |
| 평소 응답률 대비 급락 | 20 |
| 매뉴얼 6징후 | 개당 12, 합계 상한 40 |
| 식사 불량 / 심각 | 12 / 25 |
| 위생 불량 | 10 |
| 공과금 2개월 이상 체납 관찰·보고 | 10 |
| 최근 건강·정신적 괴로움 관찰 | 12 |

합계는 100에서 클램프하지만 `급성도_원합계`, `급성도_클램프_적용`, 전체 `점수_기여내역`을 함께 반환한다. `관찰_6징후.연락_두절`은 현장 관찰값이며 같은 실패 전화를 `연속_미응답_횟수`와 중복 기록하면 안 된다.

등급과 액션은 다음과 같다.

| 점수 | 등급 | 액션 |
| ---: | --- | --- |
| 0~29 | 정상 | 재연락 예약 |
| 30~54 | 주시 | 재연락 기한 단축 |
| 55~74 | 방문권고 | 담당자 승인 대기 |
| 75~100 | 방문권고-우선 | 최우선 담당자 검토 |

## 취약도 배점 v0.1.0

- 공개 동단위 구조 맥락: 고령비율·1인가구비율·노후주택·기초수급 밀도의 **상류 정규화 결과 0~50**
- 도움을 요청할 사람·기관 관계망 없음: +25
- 타인 연락이 주 1회 미만 또는 없음: +25

현재 코드는 상류에서 제공한 동단위 점수와 네 기여점의 합이 일치하는지 검사한다. 네 공개 지표를 0~50으로 정규화하는 가중치 자체는 아직 확정하지 않았으며, 임의 가중치를 구현하지 않았다.

## 권한 경계

점수 엔진은 `권고`까지만 만든다. `applyTriageVisitRecommendation`이 같은 케이스의 방문 권고를 ContactOps 상태에 반영하더라도 `visit_decision`과 `approved_visit_constraints`는 만들지 않는다. 오직 `applyManagerVisitDecision`의 명시적 담당자 결정만 `approved` 또는 `rejected`를 기록하고 승인 방문 제약을 만든다.

기존 미응답 규칙은 후속조치 상태와 기한만 만든다. 미응답 2회만으로 방문을 직접 권고하던 레거시 분기는 제거했으며, 방문 권고의 점수 기준은 이 계약 하나로 통일했다.

## 근거와 한계

필드 근거는 보건복지부 이웃연결단 매뉴얼의 발굴특성(p11), 위험징후 체크리스트(p14·p48), 가정방문기록지(p49)다. 매뉴얼은 관찰 항목의 근거이고, 배점 숫자와 임계값은 별도의 운영 배점표 v0.1.0이다. 실제 성과·편향 검증 전에는 확률이나 개인 판정으로 해석하지 않는다.

## 배점 역전 감시

```bash
npm --prefix backend run report:contact-triage
```

이 명령은 실제 65세 이상 1인세대 동별 분포로 배분한 5,869개 합성 업무 ID에 고정 시나리오를 결정적으로 배정한다. 공개 구조 맥락 0~50은 네 개 지표의 기여내역과 함께 주입하며 `[MODEL OUTPUT — UNVALIDATED]`로 유지한다.

현재 fixture의 결과는 다음과 같다.

- 정상 669, 주시 1,953, 방문권고 1,278, 방문권고-우선 1,969
- 방문권고-우선 중 고강도 기준 신호 없이 경증 누적으로 오른 사례 647건
- 현행 행정동 162개와 2025 지도구역 156개 모두 보존

647건은 실제 대상자가 아니라 **배점 튜닝 경고**다. 이 비율이 운영 의도보다 높다면 배점이나 상한을 조정한 뒤 골든셋·분포 리포트를 다시 검증해야 한다.

## 초기 운영지도 합성 시나리오

실제 연락 결과가 없는 새 세션에서도 구현된 점수·지도 계약을 확인할 수 있도록 `backend/src/contact-triage-synthetic-scenario.mjs`가 현행 행정동별 가장 작은 합성 업무 ID 1건을 고정 예시로 선택한다. 총 162개 예시가 156개 지도구역을 모두 덮으며, 급성도 채색과 취약도 원 크기는 계속 별도 축이다.

- 화면은 `데모 예시`, 기준일, 세션 기록·데모 예시·미기록 건수를 함께 표시한다. API는 `synthetic=true`와 시나리오 출처 필드로 같은 경계를 유지한다.
- 전체 5,869건을 구역 최댓값에 넣어 거의 모든 구역이 100점으로 포화되는 것을 피하기 위한 표시용 표본이다.
- 실제 세션 점수가 존재하는 케이스에는 합성 예시를 적용하지 않는다.
- 합성 예시는 ContactOps 상태, 후속조치, 방문 승인, 이관 또는 경로 제약을 변경하지 않는다.
- 공개 구조 맥락 0~50을 기여내역과 함께 주입하므로 전화 이력이 없어도 취약도 축은 표시된다. 이는 지역 집계 맥락이며 개인 관찰값이 아니다.
- `GET /api/v1/contact-ops/operations-map`의 `visit_review_points`는 이 표본 중 `권고` 상태만 급성도·취약도·케이스 ID 순으로 정렬해 제공한다. 각 점에는 공개 주거건물 도로명주소·대표좌표·건물명·아파트 여부와 점수 기여내역이 포함되어 UI가 별도 결합 없이 점 레이어를 만들 수 있다.

이는 운영 로직 시연 데이터이지 실제 주민 상태, 실제 이웃연결단 업무량 또는 개인 판정이 아니다.

## 센터 방문검토용 데모 사전 기록

서버는 별도로 현행 행정동마다 1건, 총 162건의 `demo_precontact_record` baseline을 만든다. 이는 “오늘 앞선 연락 결과가 이미 접수된 상태”를 시연하기 위한 것이며 원본 household fixture에는 급성도나 관찰값을 저장하지 않는다.

- canonical scorer의 급성도 55점 이상인 후보 중 `-0001`을 우선 제외하고, 가장 낮은 임계 통과 점수와 업무 ID 순으로 1건을 선택한다.
- `프로필_버전=demo-precontact-v1`, `revision=1`, `visit_approval_status=recommended`로 시작한다.
- 담당자 승인·반려 결정과 승인 방문 경로 제약은 만들지 않는다.
- `recommended`는 센터 방문검토에만 나타나며, `approved`가 된 뒤에만 오늘 방문 레인으로 이동한다.
- 메모리·Firestore 세션 reset은 같은 baseline으로 복귀한다. 일반 state 생성기는 `initialRecords`를 주입하지 않으면 기존 `revision=0`, `triage=null` 동작을 유지한다.

이 사전 기록도 실제 연락 기록이나 실제 주민 상태가 아닌 결정적 데모 상태다.
